## Before configuration: know the receiver's rules

Review [integer flags](/learn/c/2/), [pointers](/learn/c/5/), and [validated profiles](/learn/c/7/). This page connects C syntax to a virtual RAM interface. The next [device-foundations track](/learn/device/1/) supplies the additional controller knowledge required before treating such writes as a real configuration method.

Our RAM contract uses 0xF000 for a capacity request in MiB, 0xF004 for enable, and 0xF008 for parity mode. Width is 32 bits, addresses are four-byte aligned, and values begin at zero for each run. The functions represent local virtual storage, not an installed memory controller. The same addresses have other meanings in another lab because each workspace gets its own device profile.

## Read every operation as a cause with limited evidence

The first call records 512 at the capacity address. The second records enable one. The third records parity one. The three read calls return those recorded values, and printf displays them. Final MMIO state therefore establishes that the requested fields were written. It does not establish RAM training, refresh behavior, voltage stability, error detection, or a completed memory test.

The reference's writes are accepted in any order by this plain storage model. A real controller may demand parity setup before enable, a separate commit command, or a disabled state. The following example uses an explicit disable/configure/enable sequence, while still acknowledging that the model does not enforce it.

```c run:ordered-profile
#include <stdio.h>
int main(void) {
    mmio_write(0xF004, 0);
    mmio_write(0xF000, 512);
    mmio_write(0xF008, 1);
    mmio_write(0xF004, 1);
    printf("capacity=%u enabled=%u parity=%u\n",
           mmio_read(0xF000), mmio_read(0xF004), mmio_read(0xF008));
    return 0;
}
```

Try it in the terminal beside the explanation. Expect `capacity=512 enabled=1 parity=1`. Equal final state does not prove equal intermediate behavior on a real device. Follow the call order in **Trace** and state which controller rule would make that difference matter.

## Volatile is a narrow language property

Native volatile-qualified accesses describe observable operations under an implementation's contract. They do not make a read-modify-write atomic, coordinate two threads, flush a DMA buffer, or supply every device-ordering requirement. Real Linux drivers map their resources and use I/O accessors; DMA and shared-memory publication require their own platform protocols.

The runner parses qualifiers but does not model compiler optimization or memory ordering. Its functions make that limit explicit. Learn [acknowledgement and timeout](/learn/device/2/), [electrical timing](/learn/device/3/), and [DMA ownership](/learn/device/4/) before transferring this simple pattern to actual controllers. No additional language name removes those obligations.

## A device register is not an ordinary variable
A memory-mapped device can change independently of a CPU's instruction sequence. Native C often uses volatile-qualified access to tell the implementation that such reads and writes are observable operations. Volatile is not a lock, does not make compound operations atomic, and does not by itself supply every ordering guarantee that an architecture or device requires. Real driver code may also need barriers and platform-specific accessors.

This interpreter uses explicit functions, `mmio_write(address,value)` and `mmio_read(address)`, to represent virtual device-register access. They do not access your laptop's hardware. The calls make the simulation boundary visible and let the same lab be implemented with RV32I stores and loads. The runner rejects unaligned addresses and addresses outside the virtual register window.

## Define an interface before writing a value
For the RAM configuration lesson, 0xF000 requests capacity in MiB, 0xF004 requests enable, and 0xF008 requests parity mode. Each register has a four-byte unsigned representation. Reset values are zero. The target lab asks for capacity 512, enable one, and parity one. These are model settings chosen to illustrate configuration, not universal RAM-controller registers.

The example writes the three settings and prints the read-back values. Read-back shows that the model recorded the intended state. It is weaker than a physical stability test. In a real memory bring-up process you would also consult supported capacity, electrical timing, training status, error counters, and the controller manual.

## Reason about sequencing
A practical driver often disables a device, writes configuration, checks acknowledgement, and then enables it. A simple model may accept every write without modelling all intermediate states. When presenting the project, distinguish the model's implemented transition rules from the fuller workflow the lesson explains. Do not infer a property merely because the screen animates a component.

Run the editor and inspect MMIO to find the three stored values. Replace one address with an odd address and observe the error. Change parity to zero and run: ordinary execution still succeeds, but the hardware lab's target checks should fail. Successful execution and successful completion of a requirement are different claims.
