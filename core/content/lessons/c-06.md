## Before functions: define effects as well as results

Review [call and stack protocols](/learn/assembly/5/) and [pointer identity](/learn/c/5/). A C function has input values, a return value, and possibly effects on shared objects reached through pointers or globals. Its contract must also specify valid inputs and what state it preserves. A signature alone does not express every such condition.

The reference calls sum_to with five and ten. Each invocation initializes a new local accumulator to zero, so results are fifteen and fifty-five. A local variable's spelling does not connect it to a caller's variable of the same name. Each call has its own parameter and local objects. The interpreter represents these with virtual frames; a native compiler chooses registers, stack locations, and optimized forms under an ABI.

## A pointer is passed by value too

Try this complete program in the terminal beside the documentation.

```c run:pointer-parameter
#include <stdio.h>
void change_copy(int value) {
    value = 99;
}
void change_object(int *value) {
    *value = 42;
}
int main(void) {
    int value = 21;
    change_copy(value);
    printf("copy_call=%d ", value);
    change_object(&value);
    printf("pointer_call=%d\n", value);
    return 0;
}
```

Expect `copy_call=21 pointer_call=42`. The first function changes only its parameter object. The second receives a copied pointer value designating the caller's object, then writes through it. C still passes by value in both cases; the observable difference comes from what the copied value allows the function to reach.

## Storage duration determines what survives a return

An automatic local object's lifetime ends when its block finishes. A returned integer copies a value out; a returned pointer to an expired local does not extend that local's lifetime. Persistent global state survives function calls but creates other coordination and test-isolation obligations. A driver helper may return a status while modifying registers; both outputs must be considered.

Recursive functions require a base condition and progress toward it. Our call-depth limit bounds bad experiments but is not a proof of algorithm correctness or a native stack capacity estimate. A bounded loop can often express the same small task with clearer resource use. Before using a helper for configuration, identify whether a return value means invalid parameters, a recorded request, acknowledged completion, or a successful functional test. Those meanings should not be collapsed into one generic zero or one.

## Try this in the terminal beside the documentation

## A function separates a contract from a caller
A function declaration gives a return type, a name, and parameter types. A definition adds the body. A caller supplies argument values; the function uses its own parameter objects and returns a result. This lets a caller depend on a contract without repeating the implementation.

The example defines `int sum_to(int n)`. Its contract is to return the sum of positive integers from one through n, with zero for n less than one. The main function calls it twice. Each call gets a separate local sum and loop index. A local name inside sum_to is not a reference to a variable of the same spelling inside main.

## Parameters are passed by value
C passes argument values. Changing parameter n does not change the caller's original integer. To change a caller-owned object, pass a pointer to it and deliberately write through the pointer. That does not contradict pass-by-value: the pointer value is still copied, while both copies can designate one object.

At machine level, a calling convention chooses registers and stack locations for arguments, return values, and saved state. Your earlier assembly example made return-address preservation explicit. A C compiler supplies such sequences. The syntax-tree interpreter uses bounded virtual frames instead of pretending to emit those native instructions, so its call trace is evidence about language flow rather than compiler code generation.

## Trace the worked calculation
For n = 5, the function visits five positive integers and returns 15. For n = 10, it returns 55. The expected output is `first=15 second=55`. Notice that the second call starts from sum zero again. If sum were a global object intentionally retained between calls, that behaviour would be different; state lifetime is part of the function contract.

Functions can call themselves recursively. A correct recursive function needs a base case and progress toward it. This runner limits nested calls to forty so a missing base case cannot grow an unlimited stack. The limit is a teaching constraint, not a language restriction or a measurement of the hardware stack's size.
