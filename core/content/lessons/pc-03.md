## Before configuring a block-device profile

Review [buffer and block contracts](/learn/device/5/), [DMA ownership](/learn/device/4/), and [activation](/learn/device/2/). A block count, byte count, logical block number, queue depth, and available capacity are different quantities. Know which one the interface expects before calculating or storing a field.

## Derive the target's implications

The target requests 512 bytes per simulated logical block and a queue capacity of four requests. Logical block number three begins at byte offset `3*512=1536`. A 1536-byte contiguous payload needs three such blocks; a 1537-byte payload needs four. Four queued requests do not mean four blocks: each request can describe a different transfer length under an actual command format.

For a transfer, validate the starting block, count, end position, byte-size arithmetic, buffer capacity, and supported alignment before handing it to a device. An address calculation can overflow or fit a buffer while exceeding device capacity. A storage controller then needs a command descriptor, DMA mapping, ownership transfer, completion status, and error handling. It does not infer those from the block_bytes field.

## A completed write is not automatically durable

A device may acknowledge work after receiving it into volatile cache. A filesystem and storage stack need the device's documented persistence, ordering, and flush semantics to make a durability claim. A larger queue can improve utilization under some workloads but can also increase contention and latency; throughput is measured, not guaranteed by queue depth.

The site's profile stores three integers. It does not allocate a disk, issue reads or writes, create a filesystem, emulate a DMA ring, or survive a power failure. The model gives an inspectable storage component and target comparison so you can practice interface reasoning inside one workspace.

## Try and inspect the virtual state

Run the matching reference beside the documentation. Expect MMIO 512, 4, 1 and all three target checks passing. Change queue depth to eight; the generic write remains valid but the fixed task target fails. Set enabled to zero and note that fields remain present while the profile is disabled. Explain why neither mutation establishes a speed or persistence result.

For independent work, compute block spans for byte lengths 0, 1, 512, 513, and 1537. Expect counts 0, 1, 1, 2, and 4 under ceiling division. Then list the extra controller facts required to turn those counts into a real transfer request. An operating-system driver uses a supported device protocol; [OS foundations](/learn/os/5/) place that driver among the later kernel responsibilities.

## Try this in the terminal beside the documentation

Read the prerequisite explanation and register table before running. These two complete reference programs produce the same target MMIO values. Use the language switch above the workspace to select C or RV32I assembly, load the matching example, then press Run. Inspect **State / mmio** and the component telemetry.

```c run:reference
#include <stdio.h>
int main(void) {
    mmio_write(0xF000, 512); // block_bytes
    mmio_write(0xF004, 4); // queue_depth
    mmio_write(0xF008, 1); // enabled
    printf("Configuration written. Inspect MMIO and test checks.\n");
    return 0;
}
```

```assembly run:reference
lui t0,15
li t1,512
sw t1,0(t0)
li t1,4
sw t1,4(t0)
li t1,1
sw t1,8(t0)
li a7,10
ecall
```

Both references should pass all three address targets in the table. The starter intentionally misses one target. Passing records the configured **virtual profile**; use the guided mutations below to distinguish encoding, domain constraints and measured physical behavior. Each run starts with fresh register state.

## What this component does
A block device presents fixed-size chunks addressed by block number. A boot sector is one small example of block-oriented storage. Drivers translate software requests into a controller protocol, then use status and interrupts or polling to learn whether an operation completed.

## The virtual interface
Set a 512-byte block size, a queue depth of four, and enabled state. The model illustrates the configuration portion of a block interface. It does not load disk contents or model DMA, persistence, or failure recovery. A filesystem would add naming and allocation rules above the device, while a boot loader might read sectors before any filesystem service exists.

This lab uses a separate three-register contract for the selected configuration. Each register is a 32-bit word, starts at zero for each run, and accepts aligned word writes. The same address can have a different documented meaning in another lab; every run gets its own device state. These are teaching registers, not a vendor's real memory map.

| Address | Setting | Target | Unit and meaning |
|---|---|---|---|
| 0xF000 | block_bytes | 512 | Bytes per simulated block |
| 0xF004 | queue_depth | 4 | Concurrent requests allowed in the profile |
| 0xF008 | enabled | 1 | 1 enables the virtual block interface |

## Configure and test
The starter has one setting deliberately at zero. Read the target table and fix the configuration. Select the storage component in the model, then run C or switch to RV32I assembly. C uses mmio_write; assembly uses SW through a base register. Both should leave exactly the same final register values. The server checks the actual recorded state and only records completion when every target passes.

The component highlight and telemetry follow the run's values. They are visual evidence of this simulation's state, not a test of physical electrical behaviour. A successful write differs from a valid configuration; target checks establish the latter for the stated model. There is no prerequisite lock.

## Failure experiment
Set queue depth to zero and distinguish accepting the integer write from meeting the intended profile. Relate a 512-byte boot image in the OS workspace to a sector without claiming every real disk has the same logical or physical sector size.

Change one value at a time, predict which check will fail, and use MMIO to identify the corresponding address. Also test an unaligned address and explain why it fails before target comparison. A real configuration tool would additionally need permissions, a supported device, documented capabilities, acknowledgement, rollback, and measured feedback. This exercise isolates the interface reasoning so those future layers have a clear foundation.
