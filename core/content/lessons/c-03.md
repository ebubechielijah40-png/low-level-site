## Syntax groups familiar machine operations
An if statement selects one path based on a condition. A while loop repeats while its condition is true. A for loop puts initialisation, a condition, and an update into one form. These constructs eventually become comparisons and branches, like the assembly loops you already examined. The language groups a common pattern into a structure that is easier to read and verify.

A C condition treats zero as false and nonzero as true. The comparison `i <= n` produces either zero or one. `=` assigns; `==` compares. Assigning within a condition is legal syntax in full C and often a bug, so a parser cannot decide whether that spelling matches your intention. You need a stated expected behaviour and boundary tests.

## Derive the example
The editor starts sum at zero and visits i = 1 through i = 5. At the start of iteration i, sum is the sum of the positive integers smaller than i. Adding i preserves that invariant for the next iteration after i advances by one. The loop exits when i becomes 6, so sum contains 1 through 5 and equals 15.

A separate mathematical check is n(n+1)/2. This is valuable because it establishes the expected answer independently of the implementation. Testing a loop against another loop copied from the same logic would provide weaker evidence; both could share an off-by-one error.

## The order of operations matters
The for loop initialises i once, checks the condition before each iteration, executes the body, and then executes its update. Continue skips to the update; break leaves the loop. Moving an increment into the body or changing `<` to `<=` can change which values are visited even when the loop still terminates.

The interpreter gives every expression and statement a step cost, limits execution, and limits output size. The count is an interpreter workload metric, not a CPU-cycle measurement. It is useful for spotting an infinite loop, but not for comparing machine performance across languages.

## Controlled tests
Run the example and inspect Variables for the final sum. Change n to zero: no positive integers are visited and the sum remains zero. Change n to one: the sum is one. Change the condition to i < n and predict the missing last term. Remove the update and observe the bounded failure.
