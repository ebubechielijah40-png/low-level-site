## Before control flow: define what counts as correct

You need [C arithmetic](/learn/c/2/) and ideally [machine branches](/learn/machine/6/). A program can finish without producing the intended result. State the input domain, expected output, maintained relationship, and stopping argument before using a success label as evidence.

For the reference, n=5 and sum starts at zero. The for loop initializes i=1, checks `i<=n`, executes the body, then increments i. At the start of iteration i, sum contains exactly the terms from one through i-1. The assignment includes i. The increment restores the invariant for the next iteration. When i=6, the test is false and the accumulated sum is fifteen.

The identity n(n+1)/2 supplies an independently derived mathematical answer for nonnegative n when intermediate arithmetic is representable. “Faster” code using that expression can overflow before division even if the final mathematical result would fit. Range assumptions apply to intermediates as well as returned values.

## Boundary inputs reveal the entry rule

For n=0 the original loop has no iterations, so the result is zero. For n=1 it adds one once. If you replace the condition with `i<n`, n=5 produces ten by omitting the last term. If you move the increment before the body addition, the visited values change. Derive the sequence rather than merely rerunning until the output looks plausible.

## Try an observable loop progression

```c run:loop-trace
#include <stdio.h>
int main(void) {
    int remaining = 3;
    int sum = 0;
    while (remaining > 0) {
        sum = sum + remaining;
        printf("remaining=%d sum=%d\n", remaining, sum);
        remaining = remaining - 1;
    }
    return 0;
}
```

Try this in the terminal beside the documentation. Expect the lines `remaining=3 sum=3`, `remaining=2 sum=5`, and `remaining=1 sum=6`. Printing happens before decrement, so the visible remaining count names the term just added. Move the print after decrement and explain why its displayed remaining value changes without changing the final sum.

A `break` leaves the loop; `continue` skips the rest of the current body. In a while loop, placing its only decrement after a possible continue can prevent progress. A for loop's update still runs on continue. These semantic differences matter in timeout and polling code. The [device lifecycle lesson](/learn/device/2/) uses a bounded poll and an explicit acknowledgement, making successful termination and completed device work separate claims.

## Syntax groups familiar machine operations
An if statement selects one path based on a condition. A while loop repeats while its condition is true. A for loop puts initialisation, a condition, and an update into one form. These constructs eventually become comparisons and branches, like the assembly loops you already examined. The language groups a common pattern into a structure that is easier to read and verify.

A C condition treats zero as false and nonzero as true. The comparison `i <= n` produces either zero or one. `=` assigns; `==` compares. Assigning within a condition is legal syntax in full C and often a bug, so a parser cannot decide whether that spelling matches your intention. You need a stated expected behaviour and boundary tests.

## Derive the example
The editor starts sum at zero and visits i = 1 through i = 5. At the start of iteration i, sum is the sum of the positive integers smaller than i. Adding i preserves that invariant for the next iteration after i advances by one. The loop exits when i becomes 6, so sum contains 1 through 5 and equals 15.

A separate mathematical check is n(n+1)/2. This is valuable because it establishes the expected answer independently of the implementation. Testing a loop against another loop copied from the same logic would provide weaker evidence; both could share an off-by-one error.

## The order of operations matters
The for loop initialises i once, checks the condition before each iteration, executes the body, and then executes its update. Continue skips to the update; break leaves the loop. Moving an increment into the body or changing `<` to `<=` can change which values are visited even when the loop still terminates.

The interpreter gives every expression and statement a step cost, limits execution, and limits output size. The count is an interpreter workload metric, not a CPU-cycle measurement. It is useful for spotting an infinite loop, but not for comparing machine performance across languages.

## Controlled tests
