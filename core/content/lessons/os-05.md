## Before calling a boot artifact an operating system

Review [firmware entry](/learn/os/1/), [memory and strings](/learn/os/2/), [stack routines](/learn/os/3/), and [device ownership](/learn/device/4/). A printed boot message proves a first-stage control transfer under an environment. An operating system must also establish isolation and resource management, handle exceptions and interrupts, drive devices, and define useful interfaces for software.

The hosted site stores and emulates a private 512-byte BIOS sector. The separate `examples/minikernel` builds an ELF32 freestanding kernel for a Multiboot-compatible loader. They are separate artifacts with different loading contracts. The sector reference does not load that ELF, switch processor mode, or begin executing its kernel_main function.

## Follow source to an executable artifact

A native C compiler translates the kernel source into an object file containing instructions, data, symbols, and relocations. Assembly provides the entry code and Multiboot header. The linker combines objects under a script defining layout and resolves symbol references. A compatible loader recognizes the header, establishes its specified environment, loads the sections, and transfers control to the entry. Compilation and linking can succeed even if no loader ever executes the result.

The sample entry establishes a stack and calls kernel_main. Without a hosted runtime, the kernel cannot assume printf or ordinary libc initialization. It writes VGA character/attribute cells directly under its x86 loader assumptions. That visible screen is a next milestone, not yet a complete memory manager or scheduler.

## The missing subsystems have explicit prerequisites

| Milestone | Knowledge required | Evidence to collect |
|---|---|---|
| Native boot | executable format, loader contract, entry, stack | observed execution under a compatible emulator or hardware |
| Memory map and allocator | reserved regions, alignment, object lifetime | non-overlap, boundary and exhaustion tests |
| Exceptions and interrupts | privilege, descriptor tables, saved state | controlled exception and timer delivery |
| Virtual memory | page tables, permissions, fault handling | isolated mappings and deliberate fault tests |
| Device driver | register contract, DMA, completion, recovery | real or specified emulated transfers |
| Scheduling | contexts, stacks, preemption, synchronization | repeatable task transitions and preserved state |

These are required systems topics, not additional languages to collect. [Device foundations](/learn/device/1/) introduces the relevant interface, timing, and ownership distinctions. The site does not execute privileged instructions, emulate a full memory-management unit, or provide an ELF kernel host.

## Booting is the beginning of an operating system
A boot sector that prints text is not a complete operating system. It demonstrates a transfer from firmware to your code. A kernel must then establish and manage resources such as address spaces, interrupts, devices, timers, allocation, and scheduling. Each service needs explicit invariants and tests. A convincing project report distinguishes this stage-zero implementation from those future responsibilities.

The included `examples/minikernel` directory provides a separate freestanding C kernel with a Multiboot header, an assembly entry point, a stack, a linker script, and VGA text output. `tools/build_kernel.sh` builds an ELF executable with GNU assembler, GCC, and linker. It does not depend on a hosted C library or printf. The checked build demonstrates that the source compiles and links; it does not substitute for booting it under QEMU or compatible hardware.

## Hosted and freestanding C differ
In the hosted C lessons, a runtime calls main and supplies output functions. A freestanding kernel provides its own entry path and must arrange the environment its code needs. The assembly entry creates a stack and calls kernel_main. The C function writes character and attribute pairs into the VGA text buffer at the documented x86 address 0xB8000, under the Multiboot loader's assumed protected-mode environment.

The linker script chooses where code and data belong and keeps the boot header where a compliant loader can find it. A compiler produces object files; a linker resolves symbols and lays them out into an executable image. Compilation, linking, loading, and execution are distinct stages with distinct failure modes.

## What the site hosts today
The OS workspace stores per-user 512-byte BIOS images, makes them downloadable, and boots supported instructions inside its emulator. The emulator is intentionally limited and does not execute the separate 32-bit ELF kernel. Full-kernel browser execution would require a compatible larger emulator and loader; server execution would require a separate isolated virtual-machine service. The report records this boundary plainly.

The editor's boot message marks that boundary. Save and download it as a hosted first-stage artifact. Then build the included native kernel using the documented toolchain. Inspect its file type and Multiboot header before attempting a real boot with additional local tools.
