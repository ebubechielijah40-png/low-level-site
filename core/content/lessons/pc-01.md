## Before configuring the CPU profile

Review [register contracts](/learn/device/1/), [activation and acknowledgement](/learn/device/2/), and [clock and physical timing](/learn/device/3/). You should distinguish a core, a hardware thread, a software worker, an instruction, and a clock cycle. They measure different resources or events. A 2400 MHz request does not mean every instruction completes in one cycle or that every application executes 2.4 billion useful operations per second.

## Connect the fields to a workload

The target requests four virtual cores, a clock field of 2400 MHz, and enable one. If a chosen workload averaged two instructions per cycle on one core at that frequency, a simplistic product would be 4.8 billion instructions per second on that core. This is conditional arithmetic, not a benchmark: instruction mix, pipeline behavior, cache misses, memory bandwidth, dependency chains, and thermal throttling can change it.

Four cores can help a parallel workload only when work can be decomposed and supplied without a dominating shared bottleneck. A serial fraction limits ideal speedup; the [parallelism foundation](/learn/device/6/) gives a concrete bound. Core count is also physically constrained by the installed processor and platform. A configuration field cannot manufacture cores or establish a supported voltage/frequency operating point.

## Follow a real configuration's information requirements

Before a native frequency change, identify the processor/platform, supported operating points, firmware and kernel policy, access permissions, current workload, power/thermal limits, and how actual frequency and stability are observed. Requesting a setting, firmware accepting it, and the measured device operating at it are separate states. Platform tools generally mediate those controls; these teaching register addresses are not a universal CPU interface.

The site does not simulate pipelines, caches, clocks, voltage, power, or workload scheduling. Its target is exact final profile state. Try the program in the terminal beside the guide, then inspect **State / mmio** for 4, 2400, and 1. The selected CPU model gives context for the component being discussed; it is conceptual geometry rather than a physical layout or a performance trace.

## Make a prediction for each mutation

Changing cores to eight changes only the first target check; it proves the model records eight, not that hardware doubled. Changing enabled to zero leaves the request fields written while the active-profile target fails. Changing clock to 4800 changes the second field and target result without producing a stability experiment. Explain what measured evidence would be needed for each larger claim. Keep a written capability and acknowledgement contract before transferring this exercise to real hardware.

## Try this in the terminal beside the documentation

Read the prerequisite explanation and register table before running. These two complete reference programs produce the same target MMIO values. Use the language switch above the workspace to select C or RV32I assembly, load the matching example, then press Run. Inspect **State / mmio** and the component telemetry.

```c run:reference
#include <stdio.h>
int main(void) {
    mmio_write(0xF000, 4); // cores
    mmio_write(0xF004, 2400); // clock_mhz
    mmio_write(0xF008, 1); // enabled
    printf("Configuration written. Inspect MMIO and test checks.\n");
    return 0;
}
```

```assembly run:reference
lui t0,15
li t1,4
sw t1,0(t0)
li t1,2400
sw t1,4(t0)
li t1,1
sw t1,8(t0)
li a7,10
ecall
```

Both references should pass all three address targets in the table. The starter intentionally misses one target. Passing records the configured **virtual profile**; use the guided mutations below to distinguish encoding, domain constraints and measured physical behavior. Each run starts with fresh register state.

## What this component does
A CPU executes instructions while caches and memory supply their data. Core count and clock are different quantities: more cores can increase parallel throughput, while a clock specifies a timing rate. Neither alone establishes application performance. This model represents configuration fields, not a voltage or frequency controller.

## The virtual interface
Configure four virtual cores with an illustrative 2400 MHz request and an enable flag. Treat these settings as a resource profile. Real clock configuration also depends on supported ratios, thermal and electrical limits, firmware policy, and measurement. The model records a requested profile without simulating those physical constraints.

This lab uses a separate three-register contract for the selected configuration. Each register is a 32-bit word, starts at zero for each run, and accepts aligned word writes. The same address can have a different documented meaning in another lab; every run gets its own device state. These are teaching registers, not a vendor's real memory map.

| Address | Setting | Target | Unit and meaning |
|---|---|---|---|
| 0xF000 | cores | 4 | Virtual execution cores |
| 0xF004 | clock_mhz | 2400 | Illustrative requested clock in MHz |
| 0xF008 | enabled | 1 | 1 requests enabled state |

## Configure and test
The starter has one setting deliberately at zero. Read the target table and fix the configuration. Select the cpu component in the model, then run C or switch to RV32I assembly. C uses mmio_write; assembly uses SW through a base register. Both should leave exactly the same final register values. The server checks the actual recorded state and only records completion when every target passes.

The component highlight and telemetry follow the run's values. They are visual evidence of this simulation's state, not a test of physical electrical behaviour. A successful write differs from a valid configuration; target checks establish the latter for the stated model. There is no prerequisite lock.

## Failure experiment
Set enabled to zero and observe that valid code runs while the target fails. Double the requested clock and explain why the model can record the value without establishing a safe real operating point.

Change one value at a time, predict which check will fail, and use MMIO to identify the corresponding address. Also test an unaligned address and explain why it fails before target comparison. A real configuration tool would additionally need permissions, a supported device, documented capabilities, acknowledgement, rollback, and measured feedback. This exercise isolates the interface reasoning so those future layers have a clear foundation.
