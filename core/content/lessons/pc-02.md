## Before configuring RAM

Understand [addresses and access widths](/learn/device/1/), [activation state](/learn/device/2/), [timing and refresh](/learn/device/3/), and [arrays versus capacity](/learn/c/4/). Installed storage capacity, a controller's address map, an application's buffer allocation, and a requested virtual profile are different objects. The language can express each request only after those objects and their units are identified.

## Derive the capacity and error-detection meanings

MiB is a binary unit: 512 MiB is `512*1024*1024 = 536870912` bytes. A hypothetical contiguous byte-addressed region of that size needs 29 address bits to select its bytes. That arithmetic does not establish an actual memory chip's bank/row/column mapping, ECC organization, or controller layout. Those are specific to the installed devices and controller.

Parity adds a check bit so a chosen group has an even or odd count of ones. It detects an odd number of bit flips in that group, cannot locate a changed bit, and can miss even-numbered errors. Error-correcting schemes use more structure. This lab's parity field is a request flag; no physical error detector or ECC controller is simulated.

## Try a capacity and parity derivation beside the guide

```c run:ram-derivation
#include <stdio.h>
int main(void) {
    unsigned int capacity_mib = 512U;
    unsigned int bytes = capacity_mib * 1024U * 1024U;
    unsigned int data = 85U;
    unsigned int parity = 0U;
    for (int bit = 0; bit < 8; bit++) {
        parity = parity ^ ((data >> bit) & 1U);
    }
    printf("bytes=%u even_parity_bit=%u\n", bytes, parity);
    return 0;
}
```

Expect `bytes=536870912 even_parity_bit=0`. The eight-bit pattern 0x55 has four one-bits, so zero keeps the total even. This separate calculation does not write the lab's three target registers; its original target checks will fail while the arithmetic experiment succeeds as predicted.

## Native memory bring-up needs a controller-specific procedure

Identify installed compatible memory, supported capacity/ranks, address organization, clock and power prerequisites, part-specific command timings and refresh, firmware initialization/training, enable sequence, and feedback/error counters. Validate results with appropriate stability and integrity tests. Writing 512 cannot create physical storage, and read-back of a parity request cannot establish error protection.

The reference programs below set capacity, parity request, and enabled state in the virtual register map. Their final values establish a requested profile. Change enable to zero while parity stays one: the component telemetry must report disabled, since enable is the register at 0xF004. Change parity alone and explain why activation and error-policy request are independent. Compare the same final state in C and assembly before discussing actual memory-controller settings.

## Try this in the terminal beside the documentation

Read the prerequisite explanation and register table before running. These two complete reference programs produce the same target MMIO values. Use the language switch above the workspace to select C or RV32I assembly, load the matching example, then press Run. Inspect **State / mmio** and the component telemetry.

```c run:reference
#include <stdio.h>
int main(void) {
    mmio_write(0xF000, 512); // capacity_mib
    mmio_write(0xF004, 1); // enabled
    mmio_write(0xF008, 1); // parity
    printf("Configuration written. Inspect MMIO and test checks.\n");
    return 0;
}
```

## What this component does
RAM stores the working data a processor can access. Capacity describes how much storage exists; it is not a speed. A controller's address mapping, timing, refresh, and error reporting determine how that storage is used. This model exposes a small requested configuration so memory layout and register access can be tested together.

## The virtual interface
Request 512 MiB, enable the module, and select parity mode. Real hardware capacity is constrained by installed chips and supported address wiring; software cannot create physical capacity by writing a number. Parity can detect certain errors but is not the same as error-correcting memory. The model stores a Boolean request and makes no claim of physical error protection.

This lab uses a separate three-register contract for the selected configuration. Each register is a 32-bit word, starts at zero for each run, and accepts aligned word writes. The same address can have a different documented meaning in another lab; every run gets its own device state. These are teaching registers, not a vendor's real memory map.

| Address | Setting | Target | Unit and meaning |
|---|---|---|---|
| 0xF000 | capacity_mib | 512 | Requested virtual memory capacity in MiB |
| 0xF004 | enabled | 1 | 1 makes the model available |
| 0xF008 | parity | 1 | 1 requests the model parity flag |

## Configure and test
The starter has one setting deliberately at zero. Read the target table and fix the configuration. Select the ram component in the model, then run C or switch to RV32I assembly. C uses mmio_write; assembly uses SW through a base register. Both should leave exactly the same final register values. The server checks the actual recorded state and only records completion when every target passes.

The component highlight and telemetry follow the run's values. They are visual evidence of this simulation's state, not a test of physical electrical behaviour. A successful write differs from a valid configuration; target checks establish the latter for the stated model. There is no prerequisite lock.

## Failure experiment
Use 256 MiB and note the target mismatch. Compare the C and assembly versions at the three addresses. Explain why an allocated software buffer, installed RAM capacity, and a controller setting are three different objects.

Change one value at a time, predict which check will fail, and use MMIO to identify the corresponding address. Also test an unaligned address and explain why it fails before target comparison. A real configuration tool would additionally need permissions, a supported device, documented capabilities, acknowledgement, rollback, and measured feedback. This exercise isolates the interface reasoning so those future layers have a clear foundation.
