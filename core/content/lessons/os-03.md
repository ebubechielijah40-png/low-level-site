## Before a boot routine: establish the return path

Review [RV32I calls and stack frames](/learn/assembly/5/) and [boot strings](/learn/os/2/). x86 CALL here pushes a sixteen-bit return address on a downward-growing stack. RV32I initially places its link in a register. Both provide a return path, but the storage protocol and register names differ.

The emulator starts SP=0x7C00 with a bounded stack below the sector. A CALL reserves two bytes and places the address after CALL there. RET reads the saved address and restores SP. A nested CALL stores another return address below the first. PUSH and POP must remain balanced relative to these saved control values.

## Give print_string a precise interface

Its input is a zero-terminated string at DS:SI. It changes AL, AH, SI, and the modeled comparison condition. It returns after consuming the zero byte. It does not promise to preserve the pointer or use a returned integer status. A caller must know these clobbers before depending on a register value after the call.

## Try preserving one register explicitly beside you

```boot run:stack-preserve
bits 16
org 0x7c00
mov ax,79
call print_character
hlt
print_character:
push ax
mov ah,0x0e
int 0x10
pop ax
ret
```

Expect output `O`, final AX=79, and SP=0x7C00. CALL uses two stack bytes; PUSH uses another two; POP restores AX and RET restores the caller's position. Setting AH for firmware output temporarily changes AX, so the save/restore matters even though AL is the character of interest.

## A useful result does not prove stack correctness

If you remove POP, RET encounters the saved AX where it expects a return address. The character can already have printed correctly, followed by a failed control transfer. That is why checking only screen text is weaker than checking stack balance and trace. Conversely, a routine can restore the stack but print the wrong data; those are independent claims.

Native boot code must initialize a usable stack and appropriate interrupt/segment state before relying on calls. The teaching presets avoid that full bring-up complexity but do not remove it from a real loader's obligations. A complete kernel later needs exception paths and context-switch stack rules as well. Build a contract around each helper now so those larger boundaries are recognizable instead of mysterious.

The following is a complete program for this page's engine. Load it into the terminal beside this explanation, predict the result, then press Run. Open **State** for final values, **Trace** for recorded execution, and **Encoding** for emitted bytes when this engine supplies them.

## Control flow needs saved state
A CALL instruction transfers control and saves a return address. RET restores control from that saved address. In this x86 boot model, CALL pushes a sixteen-bit return address onto a downward-growing stack. SP tracks the current boundary. The emulator initialises SP to 0x7C00 and bounds its teaching stack below that address.

A real boot loader must establish a valid stack and relevant segment state rather than relying on the emulator's initial values. This distinction is written into the lab because a program that works in a model is not automatically ready for a firmware environment. The included sample is a small demonstration of calls, not a universal boot-loader template.

## Give the routine a contract
The routine named print_string receives a zero-terminated string address in SI. It uses AL for each character, AH for the BIOS service, and the zero flag for its stopping decision. It advances SI as it walks the string. Its caller therefore must not assume SI is preserved. A routine's contract should identify both inputs and clobbered state.

The editor prepares DS, places a message address in SI, calls print_string, and then halts. Inside the routine, the familiar LODSB/CMP/JE loop emits the string. At the terminator the routine uses RET instead of HLT, so the caller resumes after CALL. This is the distinction between finishing a helper and stopping the whole boot run.

## Observe the return path
Run and inspect the call, the body loop, and the final return. The stack pointer must return to its original value. A missing RET can make execution fall into adjacent data; an extra POP can corrupt the saved return address. The model reports bounded stack and instruction-pointer errors for those failures.

The example prints `CALL/RETURN OK`. Change the message, add a second call with another string, and verify both outputs. Explain why CALL is more than a JMP: it saves information the callee needs to resume its caller. Connect this to the earlier RV32I convention, where the first return address lived in ra and nested calls required an explicit memory save.
