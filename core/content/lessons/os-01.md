## Before boot code: the environment has changed

Review [instruction execution](/learn/machine/1/) and [calls and memory](/learn/assembly/5/). This track deliberately changes architecture from RV32I to x86 16-bit code. Register names, instruction encodings, calling conventions, and boot assumptions change with it. There is no generic machine-code language shared by every processor.

The site's boot environment loads exactly 512 bytes at address 0x7C00, initializes supported segments to zero, sets SP to 0x7C00, and begins interpreting supported x86 instructions. Those are model guarantees. Native BIOS entry state must be handled according to the actual boot convention; modern UEFI follows a different executable and service contract. A model preset is not a universal firmware promise.

## Trace the smallest visible firmware interaction

AX has two byte halves: AH is bits 15-8 and AL bits 7-0. The reference selects AH=0x0E, the BIOS teletype service, and AL=66, the ASCII code for B. INT 0x10 invokes that firmware-facing interface. The emulator implements the selected output behavior and appends B. HLT ends its bounded run.

The CPU instruction INT identifies an interrupt-vector mechanism; firmware determines what vector 0x10 means in this environment. The service selector and character data are another convention. As with the earlier teaching ECALL, output is provided by an environment, not inherent in an integer register value.

## Try two character writes in the terminal beside you

```boot run:two-characters
bits 16
org 0x7c00
mov ah,0x0e
mov al,79
int 0x10
mov al,75
int 0x10
hlt
```

Expect `OK`. AH remains 0x0E while AL changes from 79 to 75. Open **Encoding** and inspect the actual image bytes. The assembler pads unused content to byte 510 and adds signature bytes 55 AA. The image is exactly 512 bytes; that size is an artifact contract, not evidence that the sector contains an operating system.

Save and download such a sector from **Build an OS** when you want to preserve its bytes. A valid signature proves only that it matches the site's accepted sector shape. Native loading and execution are separate evidence. This emulator handles a narrow instruction and BIOS subset, has no protected-mode paging or kernel services, and treats HLT as termination rather than modeling an interruptible native halt loop.

## The processor needs an initial arrangement
An operating system cannot load itself from nothing. A machine begins with an architecture-specific reset state and firmware. Firmware initialises selected hardware and follows a boot policy to choose subsequent code. Modern systems commonly use UEFI; this learning lab deliberately models the older x86 BIOS boot-sector convention because the first executable image can be kept small and inspectable.

Under the model, BIOS loads one 512-byte sector at physical address 0x7C00 and transfers control to it in 16-bit real mode. The final two bytes must be 55 AA. This signature identifies a candidate boot sector under the convention; it does not prove the program is correct or safe on real hardware. Our emulator validates size and signature before running any image.

## A different architecture, stated explicitly
The earlier machine and assembly tracks used RV32I. This boot lab uses x86 16-bit instructions because the BIOS convention and sample boot image are x86-specific. AX, BX, CX, DX, SI, DI, SP, and BP are 16-bit registers. AL and AH are the low and high bytes of AX. These are not aliases for the earlier RISC-V registers.

`bits 16` and `org 0x7c00` are assembler directives. They describe assembly mode and label origin; they are not CPU instructions. The site's small assembler supports the documented boot subset and creates actual x86 bytes, pads unused space to byte 510, and adds the signature automatically.

## Produce observable output
The editor loads AH with 0x0E and AL with the ASCII value of B, then invokes INT 10h. The model's BIOS service interprets AH = 0x0E as teletype output and appends AL's character to the screen. HLT then stops the example. This is firmware-provided output, not printf and not an operating-system service you wrote.

Run and inspect the Boot screen. It should show B. Inspect the image length through Save image and Download: it is exactly 512 bytes. The native processor instruction HLT waits for an interrupt under relevant hardware conditions; the teaching emulator treats it as the end of this bounded run.
